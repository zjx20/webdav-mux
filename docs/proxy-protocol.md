# 下载代理协议

本文定义 webdav-mux 与“下载代理”之间的 HTTP 协议。任何实现了本协议的服务，都可以作为 webdav-mux 上游的下载代理。

## 背景

webdav-mux 是一个只读的 WebDAV 聚合服务：客户端的请求由它转发给上游 WebDAV 服务，响应体再流式回传给客户端（见 [README](../README.md)）。默认情况下，获取文件内容的 `GET`、`HEAD` 请求由 webdav-mux 直接发给上游。

给上游配置下载代理后，webdav-mux 不再直连上游取文件，而是把文件的完整 URL 交给代理，由代理取回内容后流式返回。代理用什么方式获取内容由它自己决定，例如：

- 对同一个 URL 并发发出多个范围请求，按顺序拼接后流式返回，绕过单连接限速；
- 从多个镜像地址聚合下载；
- 经由特定的出口网络访问目标。

客户端对此无感知：它收到的仍然是 webdav-mux 返回的普通文件响应，拖动进度、断点续传照常工作。

本协议的代理与常规的 HTTP 正向代理不同。常规代理（`CONNECT` 隧道或绝对 URI 形式的请求）只是一条字节通道；本协议的代理理解请求的语义，可以改变获取内容的方式。

只有获取文件内容的 `GET`、`HEAD` 经过代理，列目录的 `PROPFIND` 始终直连上游。

## 术语与约定

- **调用方**：向代理发请求的一方，即 webdav-mux。
- **代理**：实现本协议的服务。
- **目标 URL**：要获取的资源地址，也就是不使用代理时调用方会直接请求的 URL。
- **目标服务器**：目标 URL 所在的服务器，以及代理跟随重定向后到达的服务器。
- **代理基地址**：调用方配置的代理地址，协议请求的 URL 由它拼出。
- **同源**：scheme、主机、端口三者都相同。省略的端口按 scheme 的默认端口（http 为 80，https 为 443）补全，主机名不区分大小写。

文中“必须”“不得”是协议要求，违反时调用方的行为没有保证；“应当”是强烈建议；“可以”是可选行为。

## 请求

### URL

```
{代理基地址}/proxy?url={目标 URL}
```

- 代理基地址是 `http` 或 `https` 的绝对 URL，可以带路径，不带查询参数和片段。调用方去掉它末尾的 `/` 后拼接 `/proxy`。例如基地址 `http://10.0.0.2:8090/profiles/fast` 得到 `http://10.0.0.2:8090/profiles/fast/proxy?url=...`。
- 代理可以用基地址的路径区分自己内部的不同配置，比如不同的加速参数。协议不规定基地址路径的含义，调用方原样使用。
- `url` 参数按 `application/x-www-form-urlencoded` 编码，必须恰好出现一次。
- 目标 URL 必须是 `http` 或 `https` 的绝对 URL，不含用户信息（`user:pass@`）和片段（`#...`）。
- 代理必须把解码后的目标 URL 原样用于请求，不得对它的路径做“先解码再编码”之类的规范化：`%2F` 与 `/`、`%25` 与 `%` 含义不同，规范化后请求的就是另一个资源。
- 本版本只定义了 `url` 一个参数。代理遇到不认识的参数必须返回 `400`，理由见“扩展规则”。

示例：目标 URL 为 `https://nas.example.com/dav/movies/a%20b.mkv`，从第 1 MiB 开始读取：

```http
GET /profiles/fast/proxy?url=https%3A%2F%2Fnas.example.com%2Fdav%2Fmovies%2Fa%2520b.mkv HTTP/1.1
Host: 10.0.0.2:8090
Range: bytes=1048576-
Accept-Encoding: identity
```

### 方法

代理必须支持 `GET` 和 `HEAD`。`HEAD` 的响应头必须与同一请求使用 `GET` 时相同，不带响应体。其他方法返回 `405`，并带 `Allow: GET, HEAD`。协议请求没有请求体。

### 请求头

调用方只发送下表中的请求头，代理可以忽略表外的头。

| 请求头 | 含义与代理的义务 |
|---|---|
| `Range` | 见“范围请求”。 |
| `If-Match`、`If-None-Match`、`If-Modified-Since`、`If-Unmodified-Since`、`If-Range` | 见“校验值与条件请求”。 |
| `Authorization` | 目标服务器的凭据，见“凭据”。 |
| `Accept-Encoding` | 客户端可接受的内容编码，见“内容编码”。 |
| `Accept`、`Accept-Language`、`User-Agent` | 客户端的原始值，代理可以转发给目标服务器。 |

## 响应

代理的响应分两类：

1. **目标服务器的响应。** 代理取回的内容，或者按目标服务器的响应构造出来的内容，状态码反映目标服务器的结果：`200`、`206`、`304`、`416`，目标服务器返回的其他 `4xx`、`5xx`，以及代理不跟随重定向时的 `3xx`。
2. **代理自身的错误。** 代理没能拿到目标服务器的响应（连不上、超时、内部错误），或者协议请求本身不合法。这类响应必须带 `Proxy-Status` 头，见“代理自身的错误”。

目标服务器返回错误状态码时，代理应当原样返回这个状态码，并一并返回 `Retry-After`（`429`、`503`）和 `Content-Range`（`416`）。错误响应的响应体调用方不使用。

成功的响应中，调用方使用以下响应头，其余的会被丢弃：`Accept-Ranges`、`Content-Disposition`、`Content-Encoding`、`Content-Language`、`Content-Length`、`Content-Range`、`Content-Type`、`ETag`、`Last-Modified`、`Vary`。

### 范围请求

播放器靠范围请求拖动进度。代理如果忽略 `Range` 返回整个文件，结果虽然在 HTTP 语义上合法，但拖动会变得极慢，甚至失败。

- 请求带单个字节范围、且资源长度已知时，代理必须按范围返回，支持 `bytes=起-止`、`bytes=起-`、`bytes=-末尾长度` 三种形式。
  - 响应状态码为 `206`，带 `Content-Range: bytes 起-止/总长`；
  - 响应体恰好是这个范围内的字节，`Content-Length` 等于范围长度；
  - 范围末端超出资源长度时，截断到资源末尾。
- 范围完全落在资源之外时，返回 `416` 和 `Content-Range: bytes */总长`。
- 支持范围请求的代理应当在响应中带 `Accept-Ranges: bytes`。
- 只有目标服务器本身不支持范围请求时，代理才可以忽略 `Range`，返回 `200` 和完整内容。这时响应里不得带 `Accept-Ranges: bytes`。
- 请求多个范围（如 `bytes=0-1,5-6`）时，代理可以返回 `200` 和完整内容，也可以返回 `multipart/byteranges`。
- 请求不带 `Range` 时返回 `200` 和完整内容，应当带 `Content-Length`。

### 响应体的完整性

- 响应体必须与目标资源（或者它的对应范围）逐字节一致，并且与 `Content-Length`、`Content-Range` 相符。
- 响应头已经发出后，如果传输中途出错，代理必须中断连接：HTTP/1.1 直接关闭连接，HTTP/2 重置流。不得把响应正常结束，否则调用方和客户端会把截断的内容当成完整文件。

### 内容编码

`Content-Encoding`、`Content-Length`、`Content-Range` 必须描述代理实际发出的字节。具体来说：

- 代理不得在透明解压目标服务器的响应之后，仍然保留目标服务器给出的 `Content-Encoding`、`Content-Length` 或 `Content-Range`。
- 调用方发送 `Accept-Encoding: identity` 时，代理不得返回压缩编码的内容。

客户端没有发送 `Accept-Encoding` 时，webdav-mux 总是向代理发送 `Accept-Encoding: identity`。

### 校验值与条件请求

校验值指 `ETag` 和 `Last-Modified`。代理的每个响应必须属于以下两种方式之一：

- **方式一：提供目标服务器的校验值。**
  - 响应里的 `ETag`、`Last-Modified` 是目标服务器对该资源给出的真实值。
  - 条件请求头按这些真实值判断（转发给目标服务器，或者在代理本地按目标的值判断），符合 RFC 9110 第 13 节的语义：可以返回 `304`、`412`，`If-Range` 不匹配时返回完整内容。
- **方式二：不提供校验值。**
  - 响应里不得出现 `ETag` 和 `Last-Modified`。
  - 代理必须把五个条件请求头都当作不存在：不返回 `304`、`412`，`Range` 总是按请求处理。

无论哪种方式，代理都不得自己生成校验值，比如把当前时间当作 `Last-Modified`，或者给拼接出来的内容生成新的 `ETag`。

方式二之所以必须忽略条件请求头，是因为客户端手里的校验值不一定来自代理：

- 列目录的 `PROPFIND` 不经过代理，客户端从目录列表的 `getetag`、`getlastmodified` 拿到的是目标服务器的真实值，之后可能在 `GET` 里用它们发出条件请求。
- 代理没有校验值却照常判断条件时，按 RFC 这些条件都不成立：
  - `If-Match`、`If-Unmodified-Since` 得到 `412`，文件打不开；
  - `If-Range` 让 `Range` 被忽略，每次拖动都从头传输整个文件。

方式二的代价：

- 缓存协商（`304`）失效。
- 续传时不再检查文件是否变化。如果目标文件在两次范围请求之间被修改，客户端拼接出的内容会出错。对内容基本不变的媒体文件，这个代价可以接受。

### 凭据

目标服务器需要认证时，调用方把凭据放在 `Authorization` 头里发给代理，例如 webdav-mux 上游配置的 Basic 认证凭据。

- 代理只能把 `Authorization` 发给与目标 URL 同源的地址，包括代理自己跟随重定向后到达的地址。跳转到其他源之后必须去掉。
- 代理不得把 `Authorization` 当作访问代理自身的凭据，也不应当把它写进日志。
- 代理尽力携带凭据。有的获取方式带不上凭据，比如代理内部发出的分片请求不支持自定义请求头。这时代理可以换用能携带凭据的方式获取，也可以不带凭据直接请求。后一种情况下目标服务器会拒绝，代理按目标服务器的响应返回 `401`。

### 重定向

目标服务器返回重定向（`301`、`302`、`303`、`307`、`308`）时，代理可以采用以下两种处理之一。

- **代理跟随。**
  - 代理自己请求 `Location` 指向的地址，最终返回目标资源的响应，重定向过程对调用方不可见。
  - 凭据按上一节的同源规则处理。
  - 跟随次数由代理限制，超过上限时按代理自身的错误返回。
- **原样返回。**
  - 代理返回目标服务器的 `3xx` 状态码。`Location` 必须是目标服务器给出的原值，不得改写成指向代理自己的地址。
  - 调用方把 `Location` 相对目标 URL 解析成绝对地址，再用这个地址发起一次新的协议请求 `{代理基地址}/proxy?url={新地址}`。新请求是否携带凭据、最多跟随几次，由调用方决定。
  - `Location` 如果被改写成代理的地址，调用方会把它当成目标 URL，再请求代理去代理它自己。

同一个代理可以同时支持两种处理，按自己的配置选择。两种处理的区别：

- 代理跟随时，调用方与代理之间只有一次往返；凭据的去留由代理判断。
- 原样返回时，每一跳都经过调用方，多出几次往返；凭据的去留由调用方判断。

webdav-mux 作为调用方：

- 对 `GET`、`HEAD` 跟随 `301`、`302`、`303`、`307`、`308`，最多 10 次；
- 只在目标地址与上游配置的 `url` 同源时携带 `Authorization`；
- 收到没有 `Location` 的重定向，或者 `304` 以外的其他 `3xx` 时，向客户端返回 `502`。

### 代理自身的错误

响应由代理自己生成，而不是来自目标服务器时，代理必须返回 `4xx` 或 `5xx` 状态码，并带含 `error` 参数的 `Proxy-Status` 头（RFC 9209）：

```
Proxy-Status: urlproxy-helper; error=connection_timeout
```

- `Proxy-Status` 的值是一个 structured field 列表。每个成员是代理的名字（名字由代理自选），后面跟参数。
- `error` 取 RFC 9209 定义的错误类型。常见情况：

| 情况 | 状态码 | `error` |
|---|---|---|
| 协议请求不合法：缺少 `url`、`url` 重复、目标 URL 不是 http(s) 绝对地址、有不认识的参数 | `400` | `http_request_error` |
| 域名解析失败 | `502` | `dns_error` |
| 域名解析超时 | `504` | `dns_timeout` |
| 连接被拒绝 | `502` | `connection_refused` |
| 建立连接超时 | `504` | `connection_timeout` |
| 等待目标服务器的响应头超时 | `504` | `http_response_timeout` |
| TLS 证书校验失败 | `502` | `tls_certificate_error` |
| 重定向次数过多、代理配置错误、其他内部错误 | `502` | `proxy_internal_error` |

- 代理转发目标服务器的响应时，不得带含 `error` 参数的 `Proxy-Status`；可以带不含 `error` 的成员，如 `Proxy-Status: urlproxy-helper; received-status=404`。

调用方的判断规则：

- `Proxy-Status` 中任一成员带 `error` 参数，就是代理自身的错误；
- 否则就是目标服务器的响应。

区分两者，是因为同一个状态码在两种情况下的含义不同。例如代理自身返回的 `400` 表示调用方发出的协议请求有误，与客户端无关，不能原样回给客户端。

webdav-mux 的处理：

- 对代理自身的错误，`dns_timeout`、`connection_timeout`、`connection_read_timeout`、`http_response_timeout` 向客户端返回 `504`，其他类型返回 `502`，并在日志中记录错误类型。
- 对目标服务器的响应，沿用直连上游时的错误码映射（见 README 的“错误码”一节）。

### 超时

调用方等待代理响应头的时间有上限，webdav-mux 是 2 分钟。代理如果需要先探测目标（比如先取得资源长度再分片），应当在这个时间内发出响应头。响应体的传输不限时长。

## 调用方的义务

汇总前文中调用方需要做到的事：

- 按“URL”一节拼接协议请求，目标 URL 使用调用方直连时本来会用的编码；
- 只发送“请求头”一节列出的请求头；`Authorization` 只在目标 URL 与凭据所属的源同源时发送；
- 收到原样返回的重定向时，按“重定向”一节解析 `Location`、发起新请求，并限制跟随次数；
- 按 `Proxy-Status` 区分代理自身的错误和目标服务器的响应；
- 代理在传输中途中断连接时，同样中断与客户端的连接，不把截断的内容当作完整响应结束。

## 扩展规则

- 新能力通过新增查询参数来表达，比如以后可以增加改写目标请求头的参数。
- 代理遇到不认识的参数时，必须返回 `400`，并带 `Proxy-Status: ...; error=http_request_error`，不得忽略。扩展参数通常会改变获取语义，被悄悄忽略的结果是拿到错误的内容，而不是一个明确的错误。
- 调用方只在配置用到某项扩展时才发送对应的参数，所以不使用新能力的配置可以继续搭配旧版本的代理。

## 安全

- **代理会按请求去获取任意 URL。** 能访问代理的人，可以借它访问代理所在网络里的内部服务（SSRF），也可以借它消耗带宽。代理应当只部署在调用方能访问、外部无法访问的网络里，例如与 webdav-mux 同机或同一内网。
- **本版本不定义代理自身的认证**，而 `Authorization` 已被目标服务器的凭据占用。确实需要限制访问时，可以在代理基地址的路径里放一段难以猜测的随机字符串。
- **凭据可能明文传输。** 调用方与代理之间使用明文 HTTP 时，`Authorization` 里的凭据在这段链路上也是明文的。

## 实现建议：包装不完全符合协议的后端

代理常常是某个现成下载工具的一层包装：把协议请求转换成后端的格式，再把后端的响应转发回来。后端的行为不一定满足本协议。差异应当在这层包装里消化，把它包装成完全符合协议的代理，而不是让调用方去适配某个后端的特殊行为。常见的几种情况如下。

**后端在某些配置下不提供目标服务器的校验值。**

- 典型的例子是分片加速：后端把多个分片请求拼接后，用 Go 的 `http.ServeContent` 输出内容。
  - 如果传入当前时间作为修改时间，它会返回一个伪造的 `Last-Modified`。
  - 即使改传零值、不再返回 `Last-Modified`，它仍然会在“没有校验值”的前提下判断条件请求，得到 `412`，或者忽略 `Range`。
- 这时包装层应当在转发请求之前去掉五个条件请求头，并去掉后端响应里的 `ETag` 和 `Last-Modified`，使整体表现为“方式二”。
- 响应头要一起去掉：后端在加速失败、退回普通转发时，可能又带上目标服务器的真实校验值。只去掉请求头的话，会出现“有校验值却不判断条件”的响应，两种方式都不符合。
- 如果后端只在部分配置下（例如开启分片加速时）缺少校验值，只对这些配置这样处理；其余配置照常转发条件请求头和校验值，表现为“方式一”。

**后端不区分请求方法，`HEAD` 也会触发实际的数据获取。**

- 例如分片加速的后端收到 `HEAD` 时，照样先对目标发一个带范围的 `GET` 来获取资源长度，发完响应头就把这个连接丢弃。结果每个 `HEAD` 都白白占用目标服务器的一个下载连接，响应也更慢。
- 包装层可以对 `HEAD` 关闭加速，让后端对目标直接发 `HEAD`。
- 但获取路径必须与 `GET` 一致：附加的请求头、域名解析、出口网络都要相同。否则会出现 `HEAD` 失败而 `GET` 成功（或者反过来）的情况，先用 `HEAD` 探测再下载的客户端会报错。
- 校验值的处理方式也要与同一配置下的 `GET` 相同：`GET` 表现为方式二时，`HEAD` 的响应同样要去掉 `ETag` 和 `Last-Modified`。

**后端跟随重定向时，保留凭据的规则比协议宽松。**

- 例如 Go 标准库的 `http.Client` 跳转到同一主机名或它的子域名时保留 `Authorization`，不比较端口和 scheme。跳到同一主机的另一个端口，或者从 https 降级到 http，凭据都会被带过去。
- 包装层可以对带 `Authorization` 的请求关闭后端的重定向跟随，改为原样返回，由调用方按同源规则跟随。

**后端把重定向的 `Location` 改写成指向自己的地址**（为了让后续请求继续经过它）。包装层应当关闭这种改写，或者把地址还原成目标服务器的原值，否则违反“原样返回”的要求。

**后端不区分自身错误和目标服务器的错误。** 包装层至少要为自己产生的错误（比如连不上后端）加上 `Proxy-Status`。后端内部的错误无法区分时，当作目标服务器的响应转发。
